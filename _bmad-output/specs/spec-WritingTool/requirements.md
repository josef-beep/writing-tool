# WritingTool requirements

All 49 stable PRD identifiers remain first-release scope. These acceptance rules incorporate later user decisions recorded in the adopted architecture; older PRD retention/storage/recovery/date wording does not override them. Architecture details and gates remain binding.

## Functional acceptance

| ID | Requirement | Acceptance contract |
| --- | --- | --- |
| FR-1 | Manuscript formatting | Bold, italics, paragraph indents, headings and scene breaks are editable and survive save/reopen. Writing is plain text in ID-named .wrt files; the same chapter ID’s companion JSON holds chapter details and bold/italic/indent/heading/scene-break metadata. Save/reopen/revision/restore/backup/export use matching text and formatting versions. Before manuscript navigation, save automatically; on failure warn, retain edits and allow retry/cancel navigation under DEC-15. |
| FR-2 | Item restoration | View and restore individual chapter/character/event revisions. Chapters restore saved content/dates without changing linked event dates or content. Event-item restoration is a separate recovery action. Capture the Replaced revision first and resolve shared-universe conflicts manually where applicable; other partial-item dependencies remain a gate. If restored data links to an old calendar format differing from the current authority, flag the affected data as needing a calendar-format update under the shared contract/DEC-32. DEC-32 is settled: explicit Update to current calendar recalculates display from preserved elapsed positions, clears the flag only after successful save, keeps failed updates flagged/retryable and permits writing while pending. |
| FR-3 | Project restoration | Restore manuscript, plots and required saved character/event state from complete project revisions against the current authoritative universe. Resolve conflicts manually before activation; update restored project and create a new reconciled ZIP. Failed ZIP creation remains visible/retryable. If restored data links to an old calendar format differing from the current authority, flag the affected data as needing a calendar-format update under the shared contract/DEC-32. DEC-32 is settled: explicit Update to current calendar recalculates display from preserved elapsed positions, clears the flag only after successful save, keeps failed updates flagged/retryable and permits writing while pending. |
| FR-4 | Recover replaced work | Before item or project restoration persist current work in a viewable/restorable revision marked Replaced; failure blocks restoration. |
| FR-5 | Independent event editing | Chapter start and end dates are set independently; editing, assigning or clearing one never automatically changes the other, and editing both uses both entered values. Chapter date changes never modify linked main-event or flashback dates/content. The chapter view provides a link to the dedicated event editor; existing event dates/content change through an explicit event edit, not inline chapter fields or chapter-triggered shifts. Chapter operations offer no linked-update toggle or event movement/restoration selection. Exception: when both dates exist and end precedes start, set end equal to start under DEC-01; absent/valid dates and linked events otherwise remain unchanged. |
| FR-6 | Independent flashbacks | Editing a flashback historical date in the event editor updates universe placement and retains depicting-chapter links; moving/restoring its depicting chapter never changes that event date/content. |
| FR-7 | Populated calendar edits | Configure days/year and days/month with optional months; revise populated calendars while preserving elapsed positions, chronology and intervals and recalculating displayed dates. Dates alone suffice; if time is represented elsewhere it uses 24 hours/day and 60 minutes/hour. Keep entered year/day numbers as-is rather than remapping ordinary dates to an artificial year-zero day counter; the shared calendar conversion contract still preserves elapsed chronology. |
| FR-8 | Year composition | Support months only, unequal months plus standalone days, or days only; standalone days count toward year length and occupy configured positions. Minimum year data is year number plus day count; days-only mode requires no months or explicit standalone-day entries. Additional structure/names are configurable. DEC-13 requires positive whole day/month/supplied-target counts and an integer year number, with clear errors for missing required, fractional or nonnumeric values; year numbers have no fixed upper/lower bound under DEC-03. |
| FR-9 | Ordered calendar builder | Add months/standalone days linearly in any order, including standalone days before/between/after months. |
| FR-10 | Target year length | Compare target with summed month lengths and standalone days: red on mismatch, green on match. Saving mismatch is permitted and sets target to actual total; 365 target/360 actual saves 360. Populated-calendar position preservation still applies. |
| FR-11 | Element names | Both months and standalone days support names. |
| FR-12 | Optional year names | Numbered years without names can be created, saved and displayed; names may be supplied. Year numbers may be negative, zero or positive in the continuous sequence … -2, -1, 0, 1, 2 … with no fixed bounds, preserved exactly using arbitrary-precision integer semantics and no artificial epoch remapping (DEC-03 resolved). |
| FR-13 | Repeating years | The ordered year sequence and total length repeat unchanged each year under the current configuration; no leap rules. |
| FR-14 | Birth information | A year-only birth creates/updates its linked universe record at day 1, including when the year starts with a standalone day. If a birth month or day has been recorded, changing the birth year preserves those components when valid in the target year; otherwise accept the change and use the first month/day of that year (actual day 1, including a leading standalone day or a days-only calendar). Preserve linked event identity and distinguish supplied components from inferred placement. Clearing the birth year removes its linked event from the active timeline and clears the current birth association, preserving retained history; affected links must be resolved before commit. Direct birth-event date edits update the character’s displayed birth year; calendar reconfiguration displays the year containing the preserved birth position without moving the event to day 1 (DEC-19 resolved). |
| FR-15 | Character types/filter | Main, major, minor and extras classification/filtering retains every record’s accessibility; extras need only a name, with fuller optional development available. |
| FR-16 | Character fields | DEC-18: PNG/JPEG/WebP images require readable-content validation, unchanged managed copies and aspect-preserving fit without cropping/stretching; failed imports retain the previous image. Support the field matrix below; expected fields govern completeness with explicit waivers, not a save barrier. Main background is expected unless waived; specialities are optional. |
| FR-17 | Personality selection | Use all 100 exact supplied labels in the adopted catalog, names only in the selector. Zero, one or multiple selections survive save/reopen; source descriptions are reference material, not selector text. |
| FR-18 | Revision triggers | Capture complete current-work revisions every configurable interval (default 10 minutes), on normal close and before restoration. Include manuscript, plots and pinned historical universe character/event dependencies; durable pending-edit acknowledgment precedes capture/close. Autosave is separate. DEC-31: timer starts on project open/restarts on revision-interval change, one overdue capture after sleep, no overlapping captures; warn/preserve work and revisions on failure, retry next interval and offer Retry now. |
| FR-19 | Time-only retention | Architecture replaces PRD size/provider expiry rules: configurable 30-elapsed-day default applies to revisions and completed ZIPs, oldest eligible first, never by size. Protect current/retained dependencies and the ten newest valid completed ZIPs per project/standalone universe, even against manual deletion; if fewer exist protect all. |
| FR-20 | Restorable retained revisions | Every revision has a complete manifest referencing immutable content, without replay of earlier revisions; manual deletion/expiry preserves required objects/metadata and cross-unit checkpoints. No fixed minimum revision count. |
| FR-21 | Shared-content reuse | Reuse unchanged images/document versions/content within their owning store and within each complete ZIP; distinct independent ZIPs may duplicate bytes. Retained revisions resolve exact saved content. |
| FR-22 | Active-reference protection | No stored object needed by current content or retained revisions may be removed, including cross-unit history/assets. Deleting one revision must not delete shared dependencies; no references establishes eligibility without prescribing cleanup time. |
| FR-23 | Disaster recovery | Each independent complete ZIP includes a consistent current database state, retained revisions and all required images/content/reference closure. Project ZIP includes universe recovery content; standalone universe ZIP needs no project. Recover without original databases/other ZIPs; establish/reconcile one authority before project activation. If restored data links to an old calendar format differing from the current authority, flag the affected data as needing a calendar-format update under the shared contract/DEC-32. Each saved object category has its own live-storage folder; the ZIP includes those category folders and actual saved content, under the shared category-folder contract/DEC-33. SQLite/similar live database files reside in their own dedicated database folder inside their owning data folder tree; every complete ZIP automatically includes consistent recoverable database state alongside all other required data. Capture both ID-named JSON/WRT object files and the coordinated database ID/location/relationship catalog. DEC-32 is settled: explicit Update to current calendar recalculates display from preserved elapsed positions, clears the flag only after successful save, keeps failed updates flagged/retryable and permits writing while pending. |
| FR-24 | Backup triggers | Manual, configurable scheduled and normal-close backups all provide complete recovery. Scheduled backups default to 10 minutes, independently configurable from 5-minute autosave and 10-minute revisions. Failed/partial attempts never count as valid completed archives. DEC-35: project ZIP uses ProjectName_UniverseName_YYYY-MM-DD_HH-mm-ss.zip; standalone universe uses UniverseName_YYYY-MM-DD_HH-mm-ss.zip. Local real capture-start time, filesystem-safe names and _2/_3 collision suffixes apply; project ZIPs include all volumes without listing their names. DEC-34 targets open projects and independently opened standalone universes, keyed by identity; open/change timer, one overdue resume attempt, non-overlap, warning and next-interval/Retry-now paths, with one destination prompt at a time. |
| FR-25 | Backup destination | Select folders including available external drives, independently of live roots. Unavailable destinations prompt for another folder for manual/scheduled/close backups. Canceling alternate selection outside normal close skips only that attempt, reports it incomplete with retry and preserves the configured destination. Normal-close cancellation follows FR-26. |
| FR-26 | Close fallback | Canceled alternate-folder choice on normal close creates a new application-root backup folder, falling back to user-data if not writable. Save before close finishes; next launch identifies actual folder and requests a new destination. Outside-close cancellation follows FR-25; fallback-save failure and close retry behavior remain in the coordinated lifecycle gate. DEC-08: required close-save/revision/backup failure keeps the app open, preserves edits/completed work and offers Retry, another backup folder where applicable, or Cancel closing; close finishes only after required operations succeed. |
| FR-27 | Manuscript exports | DOCX, PDF, MD and TXT each support whole-story and selected-chapter exports using the shared versioned manuscript contract; DEC-06 selection approved: one story at a time, all or selected chapters in story order, titles/manuscript only, empty chapters retained with titles, no-chapter/no-selection export disabled with explanation. Save pending edits before capture; save failure offers retry/cancel. Formatting approved: DOCX/PDF preserve rich styles with each chapter on a new page, A4/2.54 cm margins/12-point serif/1.5 spacing; Markdown bold/italics/headings without paragraph indents; TXT plain text/titles with four-space indents and no bold/italic markers. Preserve paragraph breaks; scene breaks are `***` in all formats. Destination/publication approved: Save As with story/selected-chapters names and matching extension; confirm replacement, declining returns to Save As; publish after successful conversion, preserve existing output on failure; Retry/Choose another location/Cancel; show saved path/Open file/Open folder on success. DEC-06 resolved: bundle LibreOffice for headless DOCX/PDF conversion; application-owned TypeScript serializers for MD/TXT. Users need no separate LibreOffice installation. Exact dependency/packaging/font/output verification remains technical work. The shared manuscript adapter now reads plain-text .wrt writing plus associated JSON metadata under the accepted companion-JSON formatting contract (DEC-36 resolved). |
| FR-28 | Settings export | Export a valid .json file with a JSON object containing autosave/revision intervals, backup schedule/destination, theme and retention. |
| FR-29 | Settings import | Import exported settings and restore every exported value, including theme and retention. Missing fields retain current values; unknown fields are ignored with a warning; any invalid known field rejects the entire import without partial changes. Intervals are positive whole minutes and retention positive whole days; zero does not disable features. An unavailable backup destination may remain configured. |
| FR-30 | Theme | Offer light, dark and system; system follows OS theme changes. Selection survives settings export/import. |
| FR-31 | Established decisions and types | Required automatically generated, subsequently editable per-decision short name/code displayed on timeline, separate from UUID and full text; generated defaults E001… events/D001… decisions expand beyond 999 and share per-universe uniqueness; DEC-38 resolved: nonblank/trimmed, case-insensitive uniqueness, creation-order forward numbering past issued/occupied values, stable on date/order changes, live rename reflection and retained original revision codes; exact schemas/allocation/migration remain technical work. Accepted DEC-26 maker rules: at most one existing same-universe character or faction, referenced by canonical identity so renames appear automatically. Resolve affected references before maker removal. Record timeline position, decision type and decision text; Personal Decisions require a maker, Story Decisions permit none. Neither requires an event link. Support adding more decision types later in the application, saved across reopening and available for category filtering. View in timeline/character/story-arc context. DEC-26: explicit relevant-to associations support multiple same-universe characters/stories, separate from maker; character associations are universe-owned, story associations project-owned. Decision editor adds/removes associations without deleting decisions. Character/story views use their explicit associations; writing context combines selected-story and chapter-character matches. Custom-type maker/ownership rules follow approved DEC-30 in contracts.md. Hypothetical alternatives and separate reason/consequence text fields are not implied. |
| FR-32 | Resulting events and decisions | Established decisions can lead to events or directly to other established decisions, without an intermediate event. Decision/event links remain many-to-many. Removing a link makes it unresolved only if no outgoing result links of either kind remain. Incoming links do not resolve the receiving decision. DEC-28: direct decision links are many-to-many; self-links/cycles are rejected, and following decisions must have the same date or a later date. | FR-33 | Unresolved lookup | A timeline-accessible section lists selected-universe unresolved decisions with position/maker/decision and reflects current link-derived status and synchronized context. |

| FR-35 | Standalone universe events | Required automatically generated, subsequently editable per-event short name/code displayed on timeline, separate from UUID and full heading; generated defaults E001… events/D001… decisions expand beyond 999 and share per-universe uniqueness; DEC-38 resolved: nonblank/trimmed, case-insensitive uniqueness, creation-order forward numbering past issued/occupied values, stable on date/order changes, live rename reflection and retained original revision codes; exact schemas/allocation/migration remain technical work. ## Calendar display examples

Preserve `dayofyear/year` and `month/dayofmonth/yearnumber/yearname`; year names remain optional. `362/6976` means day 362 of year 6976 in an example 365-day calendar without months; 365 is not a required default. For named standalone days with a named year, use `name-of-year/dayname-daynumber/yearnumber` (for example `Dragon/Festival-40/6976`). Without a year name, use `dayname-daynumber/yearnumber` (e.g. `Festival-40/6976`), with no leading slash. Day number means day-of-year. An unnamed standalone day displays `name-of-year/daynumber/yearnumber` when the year is named, otherwise `daynumber/yearnumber`; omit missing names and their separators/hyphen. DEC-04 resolved; year names remain optional. Fictional dates and real revision/archive creation timestamps are separate contracts.
